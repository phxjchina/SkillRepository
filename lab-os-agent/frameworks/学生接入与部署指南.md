# 学生接入与部署指南（实验室 OS Agent · 学生侧）

> **直接回答彭老师的疑问**：学生**不需要**装 WorkBuddy，也**不需要**直接用 `lab-os-agent` Skill。
> Skill 是**部署者（彭老师）的操作手册**；学生面对的，是一个轻量对话入口，背后连到实验室统一部署、已加载该 Skill 的 Agent 服务。

---

## 〇、先厘清三个角色（避免混淆）

| 角色 | 是什么 | 谁用 | 类比 |
|------|--------|------|------|
| **WorkBuddy** | 彭老师的 Agent 客户端 / 运行时 | 彭老师 | 厨房 |
| **lab-os-agent Skill** | 操作手册：定义 Agent 加载哪些框架、怎么路由、怎么注入知识包、边界护栏 | 彭老师（部署时） | 菜谱 |
| **学生对话服务** | 跑着已加载 Skill 的 Agent，对外暴露一个聊天界面 | 学生 | 端上来的菜 |

一句话：**Skill 是"菜谱"，彭老师是"厨师"，学生吃的是"菜"（对话服务）。** 学生只要能"吃"，不必进厨房、不必看菜谱。

│                                                                                     │

│   │  学生登录 → 绑定 student_id → 读写 /workspace/lab-data/students/<学号>.json       │  │
│   └───────────────────────────────────┬───────────────────────────────────────────┘  │
│                                        ▼                                            │
│   ┌────────── 已加载 lab-os-agent Skill 的 Agent 运行时 ──────────┐                  │
│   │  路由 Router → 技术/情绪/制度/信念/能力/实验 6 专家（各加载自己框架 RAG）        │  │
│   └───────────────────────────────┬──────────────────────────────┘                  │
│                                     ▼                                               │
│   ┌──────────── 本地推理：Ollama + Bonsai-27B ────────────┐                          │

> **隐私内核延伸**：您一贯要求"隐私不出本机"；对学生收敛为"**不出实验室内网**"——模型在实验室服务器本地跑，学生档案只在实验室文件系统中，不经过任何外部云。

## 二、三种接入层方案对比（学生端"菜"长什么样）

| 方案 | 学生端形态 | 部署难度 | 隐私 | 学生习惯度 | 评价 |
|------|-----------|---------|------|-----------|------|
| **A · 网页 Chat（推荐）** | 浏览器打开内网网址登录即聊 | 中（一台 GPU 服务器 + 轻量前端） | ✅ 内网不出 | 一般（需记网址） | **最稳、最快上线、零学生端安装** |
| **B · 企业微信 / 微信** | 在微信里和 Agent 聊 | 高（需公网或内网穿透 / 企微后端） | ⚠️ 可能触校外云 | 最高（天天用） | 习惯最好，但合规与隐私需额外把关 |
| **C · 学生本地各自跑** | 学生自己装 Ollama 加载 | 极高（学生普遍无 GPU） | ✅ 完全本地 | — | **不现实，直接排除** |

> **推荐 A**：学期内即可上线，学生零安装（打开网址即用），隐私可控，且天然契合"小世界"的集中式叙事场——所有学生连同一个 Agent，正好强化共同体的意义感（呼应信念框架"共同体态"）。

## 二·附 部署位置权衡：实验室内网 vs 阿里云

> 彭老师问：自己有阿里云服务器，能否把服务部署上去？
> **结论**：技术上完全可以，但与"隐私不出本机/内网"的基底有冲突，需权衡。**推荐"云做网关、推理留本地"的混合架构。**

| 维度 | 实验室内网部署（推荐默认） | 全量上阿里云 | 混合（阿里云网关 + 本地推理） |
|------|------------------------|-------------|---------------------------|
| 技术可行性 | ✅ | ✅ | ✅（需一条稳定隧道） |
| 隐私 | ✅ 数据不出实验室 | ⚠️ 数据出校上公网云 | ✅ 推理与数据仍在本地 |
| 校外访问 | ❌ 仅校内 | ✅ 随时随地 | ✅ 随时随地 |
| 成本 | 零云费用（用现有机器） | 持续 GPU 实例费（月数百元起） | 仅轻量网关费（很低） |
| 模型 license | 本地自用通常无碍 | **需确认 Bonsai 是否允许云部署 / 商用** | 同本地 |
| 安全面 | 内网，攻击面小 | 公网暴露，需 HTTPS/鉴权/防注入/日志脱敏 | 网关需鉴权，攻击面中等 |

**推荐路径**
1. **默认**：实验室内网一台 GPU 机器（零云成本、隐私最优），覆盖校内 95% 场景。
2. **若需校外访问**：阿里云只放"接入网关"（反向代理 + 鉴权 + HTTPS + 静态前端），通过隧道（frp / Tailscale / 阿里云 VPN）连回本地 Ollama 推理。数据不落云、模型不在云跑，隐私基底保留。
3. **不建议**把模型权重与学生档案全放阿里云——除非您明确接受云端、确认模型 license、并补齐公网安全层（鉴权 / 加密 / 脱敏 / 审计）。

> **交底**：您一贯偏好"本地 / 离线 / 免费"，上云会引入**持续费用**与**隐私外泄面**，务必想清"便利性 vs 隐私 / 成本"的取舍。混合架构是兼顾两者的务实解；若纯图省事全上云，则前面所有"本地化/隐私不出本机"护栏都要重写为"云端安全"版本。

## 三、学生接入 4 步（彭老师侧操作清单）

| 步骤 | 彭老师做什么 | 学生感知 |
|------|-------------|---------|
| **1 · 建服务** | 在 GPU 服务器部署 Agent 服务（加载 lab-os-agent Skill）+ 为每名学生建 `lab-data/students/<学号>.json` 档案 | （无感） |
| **2 · 发入口** | 给学生一个内网网址 + 其学号账号（初始口令） | 收到"实验室 AI 助手"登录方式 |
| **3 · 冷启动引导** | Agent 首次对话带学生填"坐标说明"（三个改变 + 七层阶梯位置），写入 `belief` 字段 | 被问"你在改变自己/环境/世界哪一层？" |
| **4 · 日常运行** | 服务挂定时/事件触发（《实验室OS自动化配置.md》）：周报催收、任务卡派发、行为信号自动采集 | 被催周报、被派任务、有问题随时问 |

## 五、冷启动动机：学生凭什么用？

学生不会因"老师说要用"就真用。要把"用 Agent"和前面的**叙事框架**绑定，让他自驱：

1. **三个改变**：用 Agent 是在"改变自己 → 改变环境 → 改变世界"的进程里，不是打卡。
2. **AIOPC 做自己的产品**：Agent 帮他把手上想法孵成真产品（呼应个人发展心得），"为自己做产品"比"帮老师干活"驱动力强得多。
3. **技术教练带项目**：P1 小产品先跑通 → 制造成就感 → 自然想继续问。

> 这正是"自主性底座"的落实：**不强制使用，靠真实价值与意义感让学生主动连上来**。
